# WP-E5-11 atomic promotion preparation

`tools/prepare_e5_promotion.py` prepares a review artifact for the eventual all-50-row E5 status change. It requires a complete schema-1 manifest attesting acceptance for every E5 project ID, accepted numeric values, and accepted evidence references. It refuses incomplete or malformed input and refuses to overwrite an existing output directory.

The helper copies the supplied content tree into a new output directory, changes only the 50 E5 catalog `status: draft` fields to `status: numeric` in that copy, and writes a patch and provenance report. It does not change the source content, infer acceptance, create an acceptance manifest, edit numeric values, or apply the patch to the working tree.

**Real evidence acceptance is still required.** The fixture tests use synthetic data solely to check refusal and atomic-staging behavior; they are not evidence that any E5 row is accepted. Do not prepare or apply a promotion artifact until the applicable WP-E5-11 evidence and WP10 integration gates have passed and acceptance has been recorded by the responsible reviewers. Any generated patch remains subject to human review.

## Hardened preflight inputs

The review preparer now requires a clean Git worktree and an exact `--head`; its report records the verified Git tree and content-tree hash. Pass `--repo-root`, `--content-root`, `--manifest`, `--evidence-root`, an absent external `--output-dir`, and `--head <D_HEAD>`. Each manifest evidence `reference` is a safe POSIX-relative file path below `--evidence-root` (default: the manifest directory); every target must exist within that root. The report records each evidence file's byte count and SHA-256 and rechecks it, the manifest, and source snapshot before publication. `accepted: true` remains an attestation supplied by responsible reviewers; file existence/hash checks do not grant or infer reviewer approval.

The D/P pack-pair helper is also fail-closed: freeze D and pin its HEAD/tree, content-tree hash, `content/src/game` aggregate, CLI project hash, .NET executable/version/`--info` hash; require a clean worktree and a fresh output root outside the repository. It checks those source/toolchain values before and after each Release build. After preparing isolated P, pass P's separately built pack using `--promotion-pack` and its pinned SHA-256. The helper then requires byte-for-byte equality with D's status-pair numeric pack in addition to the parsed-pack structural check that exactly 50 E5 status fields differ. Neither helper applies a patch to canonical content.

## Promotion gate boundary

`prepare_e5_promotion.py` enforces a clean source checkout at the exact supplied HEAD, all 50 catalog IDs exactly once and still `draft`, accepted row/value attestations, and at least one accepted, non-empty, existing evidence file per row. It hashes and rechecks the manifest, evidence files, and source content while staging. It does **not** decide whether a referenced artifact supports a row, require that every applicable gate (F-T1–F-T7, A1–A8, B5 technical gates, and WP-E5-10 integration) is represented, or calculate gate pass/fail. Those are reviewer responsibilities; a manifest with `accepted: true` is an explicit reviewer attestation, not an automated finding. Passing this script or its fixture tests alone is never grounds to promote.

`build_e5_status_pack_pair.py` has a different purpose: from a separate clean, fully pinned draft commit D it can build a diagnostic draft/numeric pack pair outside the worktree. It checks cleanliness, source/toolchain pins, and that only the 50 E5 status fields differ. It does not require WP-E5-11 gate acceptance. The optional P-pack comparison checks byte identity; it does not establish that P or the values have been accepted. A final acceptance pair is therefore unavailable until D and P are separately frozen with the required evidence, then the exact clean P tuple is validated. The canonical checkout currently contains uncommitted changes, so neither helper can produce a final pinned pair from it.
